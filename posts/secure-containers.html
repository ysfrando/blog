Defining a container security baseline that actually holds in production

YM
Yusuf M
Security
May 21, 2026 Published
11 min read Reading time

A container running as root with a writable filesystem and all Linux capabilities intact is not a container — it's a process with extra steps. The isolation people assume they're getting from containerization doesn't come from the container runtime. It comes from how you configure it. Most production containers I've seen are configured with the defaults, which means most production containers are significantly less isolated than they appear.

This post is the baseline we defined for production container workloads running on Docker and Kubernetes — five controls, why each one matters, and exactly what the configuration looks like. Not a theoretical checklist. The actual settings.

Why "we use containers" is not a security posture

Container isolation is real but it's not magic. A container shares the host kernel with every other container on that node. If a process inside a container can exploit a kernel vulnerability, escalate to root, or escape the container namespace, the host is compromised — and from the host, every other container on that node is reachable.

The default Docker and Kubernetes configurations don't protect against this. A container runs as root unless you tell it not to. The filesystem is writable unless you tell it not to be. All Linux capabilities are available unless you explicitly drop them. Syscalls that have no business being called by an application process are permitted by default.

The baseline is the set of settings that close these gaps. It's not about achieving perfect isolation — it's about making container escape meaningfully harder and limiting blast radius when it happens anyway.

Control 1: Non-root user

Running as root inside a container means a process that escapes the container namespace lands on the host as root. That's game over for that node. There's no legitimate reason for an application process to run as uid 0, and most don't need to — but they will unless you explicitly configure otherwise.

In the Dockerfile, create a dedicated user and switch to it before the final CMD or ENTRYPOINT:

# Dockerfile
FROM node:20-alpine

WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production

COPY . .

# Create non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Own the app directory
RUN chown -R appuser:appgroup /app

# Switch to non-root user before running
USER appuser

EXPOSE 3000
CMD ["node", "server.js"]

In Kubernetes, enforce this at the pod level with a SecurityContext — and go further by explicitly disabling privilege escalation:

# Kubernetes: pod security context
apiVersion: v1
kind: Pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1001
    runAsGroup: 1001
    fsGroup: 1001
  containers:
  - name: app
    image: myapp:latest
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true
      runAsUser: 1001

The allowPrivilegeEscalation: false flag is as important as runAsNonRoot. It prevents a process from gaining more privileges than its parent — even if a setuid binary inside the container would otherwise allow it.

Control 2: Read-only root filesystem

A writable filesystem is a persistence mechanism. An attacker who achieves code execution inside a container can write malware, modify binaries, or drop a backdoor. A read-only root filesystem eliminates that entire class of post-exploitation technique.

Most applications don't need to write to the root filesystem at runtime. They need to write to specific directories — temp files, logs, uploads. Mount those directories explicitly as writable volumes and make everything else read-only:

# Kubernetes: read-only root filesystem with specific writable mounts
containers:
- name: app
  image: myapp:latest
  securityContext:
    readOnlyRootFilesystem: true
  volumeMounts:
  - name: tmp
    mountPath: /tmp
  - name: logs
    mountPath: /app/logs
volumes:
- name: tmp
  emptyDir: {}
- name: logs
  emptyDir: {}

The first time you apply this you'll discover every directory your application writes to — because it'll crash on startup. That's actually useful information. Applications that assumed they could write anywhere now have explicit, documented write paths.

Control 3: Drop Linux capabilities

Linux capabilities break root's all-or-nothing privilege model into discrete units. A container process running with CAP_NET_ADMIN can reconfigure network interfaces. With CAP_SYS_PTRACE it can attach to any process. With CAP_SYS_MODULE it can load kernel modules. Docker grants a default set of capabilities that most application processes have absolutely no need for.

The correct default is to drop all capabilities and add back only what's explicitly required:

# Kubernetes: drop all capabilities, add back only what's needed
containers:
- name: app
  image: myapp:latest
  securityContext:
    capabilities:
      drop:
      - ALL
      add:
      # Only add what your application actually needs.
      # Most web services need nothing added back.
      # Examples of legitimate additions:
      # - NET_BIND_SERVICE  # bind to ports < 1024 (better: run on 8080+)
      # - CHOWN             # only if container needs to chown files at start

In practice, the vast majority of web services and microservices need zero capabilities added back after dropping all. If your application needs to bind to port 80, run it on port 8080 and let Kubernetes handle the port mapping — that eliminates the NET_BIND_SERVICE requirement entirely.

The capabilities an application actually uses versus the capabilities it's granted by default are almost never the same set. Auditing this gap is one of the fastest ways to reduce your container attack surface.

Control 4: Seccomp profiles

Seccomp (secure computing mode) filters the syscalls a process is allowed to make. A container process that can only make the syscalls it legitimately needs cannot exploit a kernel vulnerability that requires a different syscall — even if the vulnerability exists on that kernel version.

Kubernetes has shipped with a default seccomp profile since 1.27 — but it's not applied unless you ask for it. The RuntimeDefault profile blocks a meaningful set of dangerous syscalls (including ptrace, reboot, mount, and others) with no application impact for standard workloads:

# Kubernetes: apply default seccomp profile
containers:
- name: app
  image: myapp:latest
  securityContext:
    seccompProfile:
      type: RuntimeDefault

For higher-sensitivity workloads, a custom profile scoped to exactly the syscalls your application makes is stronger — but requires profiling first. The --security-opt seccomp=unconfined flag in Docker and the equivalent Kubernetes config should be treated as a critical finding. Unconfined means no syscall filtering at all.

# Generate a syscall profile using Docker's built-in tracing
# Run your application under load, then extract the syscalls it actually uses
docker run --security-opt seccomp=unconfined \
  --cap-add SYS_PTRACE \
  myapp:latest &

# Use strace or the Falco syscall tracer to capture the syscall set
# Then build a custom seccomp profile from that allowlist

Control 5: Resource limits

Resource limits aren't just an operational concern — they're a security control. A container with no CPU or memory limits can consume the entire node's resources, starving every other container on that node. That's a denial of service vector available to any process that achieves code execution inside your cluster.

Every container in production should have both requests (the guaranteed allocation) and limits (the hard ceiling) defined:

# Kubernetes: resource requests and limits
containers:
- name: app
  image: myapp:latest
  resources:
    requests:
      memory: "128Mi"
      cpu: "100m"
    limits:
      memory: "256Mi"
      cpu: "500m"

The memory limit is the more important security control. When a process exceeds its memory limit, Kubernetes OOM-kills it — bounded blast radius. Without a limit, a memory leak or a memory exhaustion attack takes down the node. CPU limits prevent a single container from monopolizing compute, which matters for availability but also limits the throughput an attacker has available for brute-force or cryptomining workloads.

Putting it together: the full security context

All five controls together in a production-ready Kubernetes deployment:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      # Pod-level: non-root enforcement
      securityContext:
        runAsNonRoot: true
        runAsUser: 1001
        runAsGroup: 1001
        fsGroup: 1001
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: app
        image: myapp:latest
        ports:
        - containerPort: 3000
        # Container-level security controls
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          runAsNonRoot: true
          runAsUser: 1001
          capabilities:
            drop:
            - ALL
        # Resource limits
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "500m"
        # Explicit writable mounts only
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: app-logs
          mountPath: /app/logs
      volumes:
      - name: tmp
        emptyDir: {}
      - name: app-logs
        emptyDir: {}

Enforcing the baseline at scale

A baseline nobody enforces is a doc nobody reads. Two controls make this stick across a cluster without requiring every team to get it right independently.

First, a PodSecurityAdmission policy at the namespace level. Kubernetes ships with three built-in policy levels — privileged, baseline, and restricted. The restricted profile enforces most of what's in this post: non-root, no privilege escalation, seccomp, dropped capabilities. Apply it to all production namespaces:

# Label production namespaces to enforce restricted policy
kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

Second, a Conftest or OPA Gatekeeper policy in CI that fails any deployment manifest missing the required security context fields — before it reaches the cluster:

# conftest/policies/container_security.rego
package main

deny[msg] {
  container := input.spec.template.spec.containers[_]
  not container.securityContext.readOnlyRootFilesystem
  msg := sprintf("Container '%s' must set readOnlyRootFilesystem: true", [container.name])
}

deny[msg] {
  container := input.spec.template.spec.containers[_]
  not container.securityContext.allowPrivilegeEscalation == false
  msg := sprintf("Container '%s' must set allowPrivilegeEscalation: false", [container.name])
}

deny[msg] {
  container := input.spec.template.spec.containers[_]
  not container.resources.limits.memory
  msg := sprintf("Container '%s' must define a memory limit", [container.name])
}

What the baseline actually prevents

It's worth being explicit. These five controls don't make containers unbreakable. A sufficiently motivated attacker with a kernel exploit can still escape a hardened container. What they do is raise the cost significantly and bound the blast radius when something does go wrong.

Non-root prevents a container escape from landing as root on the host. Read-only filesystem prevents persistence and binary tampering. Dropped capabilities remove the most commonly-exploited privilege escalation vectors. Seccomp blocks the syscalls that kernel exploits typically require. Resource limits contain the operational impact of a compromised container.

The question isn't whether containers can be escaped. They can. The question is what an attacker can do after they escape — and whether your baseline makes the answer "very little" instead of "everything."

None of these settings require application changes in most cases. They require someone to write them down, apply them as defaults, and enforce them in CI. That's the gap between "we use containers" and "our containers are hardened." It's smaller than most teams think.
