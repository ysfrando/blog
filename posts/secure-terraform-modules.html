Secure-by-design Terraform: AWS guardrails developers actually deploy

YM
Yusuf M
Security
May 21, 2026 Published
11 min read Reading time

The Terraform module took two weeks to build. It saved the next six months of security review findings. Every team that used the S3 module got encryption at rest, versioning, and public access blocking by default — not because they read a security doc, but because those were the only options the module exposed.

That's the idea behind secure-by-design infrastructure: encode the security baseline into the thing developers reach for, so the secure path and the easy path are the same path. This post walks through how we built reusable Terraform modules for AWS — covering WAF, S3, and IAM — with security guardrails that ship with every deployment and can't be accidentally left out.

The problem with raw Terraform

Left to write raw Terraform, developers make the same set of decisions repeatedly — and make the same mistakes repeatedly. An S3 bucket gets created with acl = "public-read" because that's what the Stack Overflow answer used. An IAM role gets AdministratorAccess because it was faster than figuring out the right policy. A WAF resource gets created with no rules because the managed rule groups weren't obvious from the docs.

None of these are malicious decisions. They're time-pressure decisions. The developer's goal is a working deployment, not a secure one — and if the secure configuration requires more research than the insecure one, the insecure one ships.

The module pattern inverts this. Security engineers write the module once, with the secure configuration as the default. Developers call the module with a handful of required inputs. The security decisions are already made.

Module design principles

Before the code, the design constraints that shaped every module we built:

Secure defaults, not secure options. Security properties are on by default and require explicit opt-out to disable — not explicit opt-in to enable. A developer who doesn't think about encryption gets encryption. A developer who needs to disable a default for a legitimate reason can, but they have to do it deliberately, with a comment explaining why.

Minimal required inputs. The module should be callable with as few required variables as possible. Every required variable is friction; friction gets bypassed. If a security property doesn't vary between deployments, it's a default, not a variable.

No escape hatches for dangerous patterns. Some inputs simply don't exist. There's no make_public variable on the S3 module. There's no allow_wildcard_actions variable on the IAM module. If a team has a legitimate edge case, they talk to the security team — they don't configure their way around the module.

The S3 module

S3 buckets have a short list of security properties that should be true in virtually every deployment: public access blocked, server-side encryption enabled, versioning on, access logging enabled, and SSL enforced for all requests. The raw Terraform to configure all of these correctly is verbose and easy to get wrong. The module makes it one call.

# modules/s3_secure/main.tf
 
resource "aws_s3_bucket" "this" {
  bucket = var.bucket_name
  tags   = var.tags
}
 
# Block all public access — no variable, always on
resource "aws_s3_bucket_public_access_block" "this" {
  bucket                  = aws_s3_bucket.this.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
 
# Encryption at rest — AES256 default, KMS if key provided
resource "aws_s3_bucket_server_side_encryption_configuration" "this" {
  bucket = aws_s3_bucket.this.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = var.kms_key_id != null ? "aws:kms" : "AES256"
      kms_master_key_id = var.kms_key_id
    }
    bucket_key_enabled = true
  }
}
 
# Versioning — on by default, can be disabled with justification
resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = var.versioning_enabled ? "Enabled" : "Suspended"
  }
}
 
# Enforce SSL — bucket policy denies non-HTTPS requests
resource "aws_s3_bucket_policy" "this" {
  bucket = aws_s3_bucket.this.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "DenyNonSSL"
      Effect    = "Deny"
      Principal = "*"
      Action    = "s3:*"
      Resource  = [
        aws_s3_bucket.this.arn,
        "${aws_s3_bucket.this.arn}/*"
      ]
      Condition = {
        Bool = { "aws:SecureTransport" = "false" }
      }
    }]
  })
}
# modules/s3_secure/variables.tf
 
variable "bucket_name" { type = string }
variable "tags"        { type = map(string); default = {} }
variable "kms_key_id"  { type = string; default = null }
 
variable "versioning_enabled" {
  type        = bool
  default     = true
  description = "Disable only for high-churn buckets where versioning cost is prohibitive. Requires security team sign-off."
}

Calling the module requires exactly one input:

# How a developer uses it
module "uploads_bucket" {
  source      = "git::https://github.com/your-org/terraform-modules//s3_secure"
  bucket_name = "myapp-uploads-prod"
  tags        = { env = "prod", team = "payments" }
}
# Public access blocked, encrypted, versioned, SSL-enforced.
# Developer made zero security decisions.

The IAM role module

IAM is where the most dangerous configurations live, and where the module pattern pays off most. The three things we enforce unconditionally: a permissions boundary on every role, no wildcard actions in inline policies, and a required description field so every role has a documented purpose.

# modules/iam_role/main.tf
 
resource "aws_iam_role" "this" {
  name                 = var.role_name
  description          = var.description  # required — no default
  assume_role_policy   = var.assume_role_policy
  permissions_boundary = local.boundary_arn
  tags                 = var.tags
}
 
locals {
  # Boundary ARN is derived from the account ID — no way to skip it
  boundary_arn = "arn:aws:iam::${data.aws_caller_identity.current.account_id}:policy/ServiceRoleBoundary"
}
 
data "aws_caller_identity" "current" {}
 
# Inline policy — validated for wildcards before apply
resource "aws_iam_role_policy" "this" {
  count  = var.inline_policy != null ? 1 : 0
  name   = "${var.role_name}-policy"
  role   = aws_iam_role.this.id
  policy = var.inline_policy
}
 
# Validation: reject wildcard actions in inline policies
locals {
  policy_doc     = var.inline_policy != null ? jsondecode(var.inline_policy) : null
  has_wildcards  = var.inline_policy != null ? anytrue([
    for stmt in local.policy_doc.Statement :
    contains(tolist(try(tolist(stmt.Action), [stmt.Action])), "*")
  ]) : false
}
 
# Terraform will refuse to apply if wildcards are found
resource "null_resource" "wildcard_check" {
  count = local.has_wildcards ? 1 : 0
  provisioner "local-exec" {
    command = "echo 'ERROR: Wildcard actions (*) are not permitted in IAM inline policies. Scope your actions explicitly.' && exit 1"
  }
  lifecycle { replace_triggered_by = [aws_iam_role.this] }
}
# modules/iam_role/variables.tf
 
variable "role_name"          { type = string }
variable "description"        { type = string }  # required, no default
variable "assume_role_policy" { type = string }
variable "inline_policy"      { type = string; default = null }
variable "tags"               { type = map(string); default = {} }
# permissions_boundary is NOT a variable — it's always applied

The wildcard check is the most important piece. It turns a security review finding into a Terraform plan failure — the policy gets rejected before it ever reaches AWS.

The WAF module

WAF configuration has the steepest learning curve of the three. AWS Managed Rule Groups cover the most common attack patterns — OWASP Top 10, known bad inputs, IP reputation — but the defaults aren't on, the priority ordering isn't obvious, and logging requires a separate resource that's easy to forget. The module handles all of it.

# modules/waf/main.tf
 
resource "aws_wafv2_web_acl" "this" {
  name  = var.name
  scope = var.scope  # REGIONAL or CLOUDFRONT
 
  default_action {
    allow {}  # default allow; rules block specific patterns
  }
 
  # AWS Core Rule Set — OWASP Top 10 coverage
  rule {
    name     = "AWSManagedRulesCommonRuleSet"
    priority = 10
    override_action { none {} }
    statement {
      managed_rule_group_statement {
        name        = "AWSManagedRulesCommonRuleSet"
        vendor_name = "AWS"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "${var.name}-common-rules"
      sampled_requests_enabled   = true
    }
  }
 
  # Known bad inputs — SQLi, XSS, command injection patterns
  rule {
    name     = "AWSManagedRulesKnownBadInputsRuleSet"
    priority = 20
    override_action { none {} }
    statement {
      managed_rule_group_statement {
        name        = "AWSManagedRulesKnownBadInputsRuleSet"
        vendor_name = "AWS"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "${var.name}-bad-inputs"
      sampled_requests_enabled   = true
    }
  }
 
  # Rate limiting — configurable, but always present
  rule {
    name     = "RateLimitRule"
    priority = 1  # evaluated first
    action { block {} }
    statement {
      rate_based_statement {
        limit              = var.rate_limit
        aggregate_key_type = "IP"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "${var.name}-rate-limit"
      sampled_requests_enabled   = true
    }
  }
 
  visibility_config {
    cloudwatch_metrics_enabled = true
    metric_name                = var.name
    sampled_requests_enabled   = true
  }
}
 
# Logging — always enabled, no variable to skip it
resource "aws_wafv2_web_acl_logging_configuration" "this" {
  log_destination_configs = [aws_cloudwatch_log_group.waf.arn]
  resource_arn            = aws_wafv2_web_acl.this.arn
}
 
resource "aws_cloudwatch_log_group" "waf" {
  name              = "/aws/waf/${var.name}"
  retention_in_days = var.log_retention_days
}

# modules/waf/variables.tf
 
variable "name"  { type = string }
variable "scope" {
  type    = string
  default = "REGIONAL"
  validation {
    condition     = contains(["REGIONAL", "CLOUDFRONT"], var.scope)
    error_message = "scope must be REGIONAL or CLOUDFRONT"
  }
}
 
variable "rate_limit" {
  type        = number
  default     = 2000
  description = "Max requests per 5-minute window per IP. Lower for sensitive endpoints."
}
 
variable "log_retention_days" {
  type    = number
  default = 90
  # Can be increased, not decreased below 90
  validation {
    condition     = var.log_retention_days >= 90
    error_message = "WAF log retention must be at least 90 days for compliance."
  }
}

Enforcement: making the modules the only path

Modules are only as effective as their adoption. A module that exists but isn't required is just a suggestion. Two controls make adoption mandatory rather than optional.

First, an SCP that prevents raw aws_s3_bucket, aws_iam_role, and aws_wafv2_web_acl resources from being created without the required tags that the modules automatically apply. Any Terraform that bypasses the module won't have the tags and will be rejected by AWS before it provisions anything.

// SCP: Deny S3 bucket creation without required security tags
{
  "Effect": "Deny",
  "Action": "s3:CreateBucket",
  "Resource": "*",
  "Condition": {
    "Null": {
      "aws:RequestedRegion": "false",
      "s3:x-amz-acl": "false"
    },
    "StringNotEquals": {
      "aws:RequestTag/managed-by": "terraform-secure-module"
    }
  }
}

Second, a Checkov custom check in CI that verifies any aws_s3_bucket, aws_iam_role, or aws_wafv2_web_acl resource in a PR is instantiated via the approved module source — not written inline.

# .checkov/custom_checks/require_approved_modules.py
from checkov.terraform.checks.resource.base_resource_check import BaseResourceCheck
from checkov.common.models.enums import CheckResult, CheckCategories
 
APPROVED_MODULE_SOURCE = "git::https://github.com/your-org/terraform-modules"
 
class RequireApprovedS3Module(BaseResourceCheck):
    def __init__(self):
        super().__init__(
            name="Ensure S3 buckets use the approved secure module",
            id="CKV_CUSTOM_S3_MODULE",
            categories=[CheckCategories.ENCRYPTION],
            supported_resources=["aws_s3_bucket"]
        )
 
    def scan_resource_conf(self, conf):
        # If the resource is defined directly (not via module), fail
        module_source = conf.get("__module_source__", "")
        if APPROVED_MODULE_SOURCE not in module_source:
            return CheckResult.FAILED
        return CheckResult.PASSED

What this looks like at the end

A developer who needs an S3 bucket, an IAM role, and a WAF for their new service writes roughly 20 lines of Terraform calling three modules. They get encryption, public access blocking, SSL enforcement, a permissions-bounded IAM role with wildcard validation, and a WAF with OWASP managed rules and rate limiting — without making a single security decision themselves.

The security decisions were made once, by the team that built the modules, with the threat model in front of them. Every subsequent deployment inherits those decisions for free.

That's the return on the two weeks it took to build. Not a one-time audit finding. Not a review gate. A security baseline that scales with the org because it's built into the infrastructure teams already use.

Secure-by-design doesn't mean making security invisible. It means making the secure choice the default choice — so developers aren't making security decisions they're not equipped to make.

The modules are the paved road. The SCPs and CI checks are the guardrails on the sides. Together they mean the question isn't "did this team follow the security guidelines" — it's "did this team's infrastructure provision successfully." If it did, it's already compliant.
