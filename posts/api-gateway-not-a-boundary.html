Your API gateway is not a security boundary

YM
Yusuf M
Security
May 21, 2026 Published
10 min read Reading time

The API gateway handled auth. That was the assumption. It wasn't written down anywhere — it was just understood. So when one internal service started accepting requests directly from another without validating the JWT, nobody flagged it. Why would they? The gateway was there.

That's the misconfiguration I've seen exploited more than almost any other in microservices environments. Not a clever zero-day. Not a complex attack chain. Just a team that treated the gateway as a perimeter and gutted every security check behind it.

What the gateway actually does

API gateways — AWS API Gateway, Kong, Nginx, Envoy, whatever you're running — are routing and policy enforcement layers. They terminate TLS, validate tokens at the edge, rate limit, and handle cross-cutting concerns so individual services don't have to. That's genuinely useful. The problem is what teams infer from it.

The inference is: if a request made it through the gateway, it's been authenticated and authorized. That inference is wrong in several important ways, and understanding why requires thinking about what the gateway can and can't see.

The gateway validates that a token exists and is signed correctly. It does not know what that token is allowed to do inside your specific service. It does not validate business-level authorization — whether user A is allowed to access resource B. And critically, it only sees traffic that flows through it. Any request that doesn't touch the gateway — internal service-to-service calls, background jobs, admin interfaces, direct VPC access — gets none of that validation.

The three failure patterns I've seen directly

1. Internal services with no auth

This is the most common. The gateway sits in front of your public API and enforces token validation. Behind it, services call each other over internal networking — and because "internal" is assumed to mean "trusted", those calls have no authentication at all.

In practice, "internal" means reachable from anything else in that VPC, that cluster, or that network segment. Compromise any workload in that environment — a misconfigured Lambda, a container with a vulnerable dependency, an EC2 instance with overpermissioned IAM — and you can call those internal services directly, with no token, no authorization check, nothing.

# What an attacker does after getting internal network access:
# Direct call to an internal service that skips the gateway entirely
curl http://orders-service.internal:8080/api/v1/orders \
  -H "Content-Type: application/json"
# No Authorization header. No gateway. Full access.

I've seen this in environments that had sophisticated edge security — WAF, DDoS protection, JWT validation at the gateway — with completely open internal services. The perimeter was hardened. The interior was flat.

2. JWT forwarding without re-validation

A subtler variant: the gateway validates the token and forwards it to the upstream service. The upstream service receives the JWT in the Authorization header and… passes it along to the next service in the call chain. Which passes it to the next. Each service assumes the previous one validated it.

// Common pattern — service B trusts whatever service A forwarded
app.get('/internal/user-data', (req, res) => {
  // Token was validated at the gateway, so we trust it here, right?
  const userId = req.headers['x-user-id']; // Set by service A
  return db.getUserData(userId);
});

The x-user-id header is set by Service A. But if an attacker can call Service B directly — bypassing Service A — they set that header themselves. There's no signature, no cryptographic binding, no verification that the header value matches a real authenticated user. It's just a string anybody can send.

The fix is not complicated: every service that does anything sensitive must validate the JWT itself, not rely on a header set by an upstream service it didn't authenticate.

3. Authorization at the gateway instead of the service

Some teams push authorization logic — not just authentication, but "is this user allowed to do this action" — into the gateway layer. Route-level policies: GET /admin/* requires role admin, and so on.

This feels clean. It centralizes policy. In practice it creates a brittle coupling between your routing layer and your business logic, and it almost always has gaps. Route-level authorization can't reason about resource ownership. It can't check whether user A owns the specific record they're trying to access at /orders/123. That check has to happen in the service, with access to the data.

# Gateway policy: users with role "user" can access GET /orders/:id
# But this doesn't check whether the order belongs to THIS user
GET /orders/456  →  allowed (user has "user" role)
# An attacker enumerates order IDs and reads other users' orders
GET /orders/457  →  allowed
GET /orders/458  →  allowed

That's an IDOR. The gateway let it through because the route was allowed. The service didn't check ownership because "the gateway handles auth." Both layers partially handled authorization and neither did it completely.

What a real defense-in-depth model looks like

The gateway stays. It's still useful for what it's good at: edge token validation, rate limiting, TLS termination, request routing. But it becomes one layer in a model that has enforcement at every tier, not the single enforcement point everything else depends on.

mTLS for service-to-service calls

Every internal service call should use mutual TLS. Each service has a certificate; each call is cryptographically authenticated in both directions. An attacker who compromises one workload and tries to call another service needs a valid certificate, not just network access.

In a Kubernetes environment, a service mesh like Istio or Linkerd handles this transparently. In AWS, ACM Private CA with automated certificate rotation via cert-manager is the pattern. The key outcome: "internal network reachable" no longer means "can call any service unauthenticated."

# Istio: enforce mTLS across the entire mesh
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: production
spec:
  mtls:
    mode: STRICT

Per-service authorization, not gateway-level

Every service must validate the JWT it receives — not trust a forwarded header, not assume an upstream service did it. The gateway's validation proves the token was valid at the edge; the service's validation proves the token authorizes this specific action on this specific resource.

Authorization logic — ownership checks, role checks, resource-level access control — lives in the service layer, next to the data. Not in the gateway, not in a shared middleware library that gets called inconsistently, but in the handler for each operation that needs it.

// Correct: service validates JWT and checks resource ownership
app.get('/orders/:orderId', authenticateJWT, async (req, res) => {
  const order = await db.getOrder(req.params.orderId);

  if (!order) return res.status(404).json({ error: 'Not found' });

  // Authorization check: does this token's subject own this order?
  if (order.userId !== req.user.sub) {
    return res.status(403).json({ error: 'Forbidden' });
  }

  return res.json(order);
});

Network policy as a hard backstop

Even with mTLS and per-service auth, network policy is cheap defense-in-depth. In Kubernetes, NetworkPolicy resources restrict which pods can talk to which other pods at the network level — before any application code runs. In AWS, security group rules between services serve the same role.

# Kubernetes NetworkPolicy: only allow orders-service to call user-data-service
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: user-data-ingress
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: user-data-service
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: orders-service

This doesn't replace mTLS or application-level auth. It adds a layer that operates independently — a compromised workload that isn't orders-service can't reach user-data-service at all, regardless of what credentials it has.

The mental model shift

The underlying issue isn't a specific misconfiguration — it's a mental model. The gateway-as-perimeter model imports a network security assumption (trust inside the boundary) into an application security context where it doesn't hold. In a microservices architecture, there is no meaningful inside. Services are independently deployable, independently scalable, and independently compromisable. Each one needs to behave as if the request it's receiving could be from an attacker.

Zero trust isn't a product you buy. It's the recognition that "this request came from inside the network" is not an authorization decision.

The gateway is a useful piece of infrastructure. It's not a security boundary. The sooner that distinction is explicit in your architecture documentation, your threat models, and your code review checklist, the fewer services you'll ship that only look secure from the outside.

Where to start if this describes your environment

  1. Map every service-to-service call in your environment. Which ones have authentication? Which ones rely on network trust? This inventory alone will surface your highest-risk paths.
  2. Audit your JWT validation. For every service that handles sensitive data, verify it validates the token itself — not a forwarded header from an upstream service.
  3. Enforce mTLS at the mesh level. If you're on Kubernetes, set PeerAuthentication to STRICT across your production namespace. If you're not, start with your highest-risk service pairs.
  4. Add network policy as a backstop. Even coarse-grained policies that restrict which services can talk to which others reduce your blast radius significantly.
  5. Move authorization checks into service handlers. Find every place you're relying on gateway-level route authorization for resource-level access control and fix it at the source.

None of this requires a platform rewrite. It requires treating each service as a trust boundary — because in practice, it already is one. You're just not enforcing it yet.
