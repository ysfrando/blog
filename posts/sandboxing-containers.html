Server-side sandboxing: Containers and seccomp

YM
Yusuf M
Security Engineering
December 26, 2025 Published
11 min read Reading time

When you run untrusted code, you need to think carefully about what that code can actually do on your system. Containers and seccomp give you meaningful isolation without the overhead of full virtual machines.

Why not just use VMs?

Virtual machines give strong isolation but come with real costs: slow startup times, significant memory overhead per instance, and operational complexity. For workloads that need to spin up and tear down rapidly, these costs are prohibitive.

Container isolation fundamentals

Linux containers combine kernel features: namespaces isolate the container's view of system resources, cgroups limit resource consumption, and capabilities restrict privileged operations. By default, containers still share the host kernel — what makes them fast also makes them less isolated than VMs.

Enter seccomp

Seccomp (secure computing mode) is a Linux kernel feature that lets you restrict which system calls a process can make.

Seccomp doesn't just reduce the attack surface — it redefines it. You only need to worry about the small set of syscalls you've explicitly permitted.
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    {
      "names": ["read", "write", "open", "close",
                "stat", "fstat", "mmap", "exit_group"],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}

Building a minimal allowlist

We use strace in audit mode to record every syscall made during integration tests, then build an allowlist from that. This process surfaced surprising dependencies — glibc's malloc occasionally calls madvise, which you'd never know to include without tracing.

Defense in depth

The value comes from layering controls: namespace isolation limits blast radius, capability dropping removes privilege escalation vectors, and seccomp blocks kernel attack surface.
